What it does

Apache-2.0 TypeScript harness from the MemGPT/Letta team that gives agents memory, identity, and experience over long horizons — and lets them rewrite their own memory blocks, skills, and the harness around them via trusted local 'mods'.

How it works

  • Memory is a three-tier git-backed projection, tiered by who may write it. Message history is *recall memory* — written by the harness and explicitly "cannot be mutated"; memory blocks (core memory, the `<self>` block projecting to `persona.md`, under `system/` in memfs-v1) are editable segments of the compiled system prompt; external memory holds skills (`skills/<name>/SKILL.md`) and markdown/reference files. The two mutable tiers are projected to MemFS at `$MEMORY_DIR` and edited with ordinary file tools plus git, with `[[path]]` links from blocks acting as "synapses" for discovery. A pre-commit hook enforces frontmatter (memfs-v1: non-empty `description`, only `description`/legacy `limit`/protected `read_only` keys allowed; memfs-v2: frontmatter-free root `MEMORY.md`, other files exactly `name` + `description`), rejects unknown keys, and blocks writes to `read_only` files; size budgets come from a memory-constraints config (`maxDepth`, `maxFileCharacters`, `maxCoreMemoryCharacters`, per-glob `fileCharacterLimits`). Edits never apply mid-turn — the prompt is compiled at conversation start, so a change lands on the next recompile.
  • Mods are the harness-rewriting tier, and they are deliberately "trusted local code", not a versioned plugin SDK: a mod is a single TS file whose default export is `activate(letta)`, loaded from `~/.letta/mods/*.ts` (machine-global, the documented default) or `$MEMORY_DIR/mods/*.ts` (travels with one agent's MemFS), activated at app start and on `/reload`. `src/mods/README.md` states the thesis outright — "Because the interface is the agent, not a human plugin author... The replacement for traditional API stability is recoverability" — so mods are assumed to be written, broken, and repaired by the agent. The registry covers `tools`, `commands`, `events`, `permissions`, `providers`, and `ui.panels`, each registration gated on `letta.capabilities` because surfaces differ (TUI/headless load panels; the desktop listener does not).
  • Mods alter execution, not just configuration. The event map is `conversation_open/close`, `tool_start/end`, `turn_start/end`, `compact_start/end`, `llm_start/end`, and four events return results that change the run: `turn_start` can rewrite the outbound message array or cancel the turn, `tool_start` can rewrite a tool call's args or substitute a synthesized result, `tool_end` can replace the result, and `turn_end` can force continuation with new input. Permission overlays return `allow`/`ask`/`alwaysAsk`/`deny` per call, provider mods register local model providers, and commands can `fork()` a scoped conversation and drive it with `sendMessageStream`. Two hard limits: mods may not import harness internals (`@/backend`, `@/cli` are off-limits), and the base system prompt is not editable — the shipped prompt says editing it directly "marks it as custom and permanently detaches you from those upgrades".
  • Safety is recovery-first, with one real sandbox. `--no-mods` / `LETTA_DISABLE_MODS=1` disables everything with no half-enabled state; `/reload` invalidates stale activations by generation (stale-handle use is itself a diagnostic); and breakage surfaces as owner/path/phase/capability-attributed diagnostics in `~/.letta/mods/diagnostics/latest.json`, so an agent can read the failure, edit the mod, and reload without a human debugging. Unattended memory subagents run under a fail-closed kernel sandbox (`src/memory-confinement.ts`): the process "can read the host broadly, write harness state and its own memory, and cannot read or write other agents' memory", and it throws rather than run under a weaker policy. The repo dogfoods the loop: `scripts/mod-learning/learn-mod.ts` and `/mods learn memory-citations` have a headless agent generate a candidate mod, evaluate it under `LETTA_MODS_DIR` against assertions such as `mod_loads`, `turn_start_injects_message`, and `tool_start_rewrites_args`, write artifacts to `.letta/mod-learning-runs/`, and never install the passing candidate automatically.

Key advantages

  • The clearest product statement of harness self-modification as a first-class, prompt-level concept. The shipped system prompt carries a section titled "Self-evolution: memory, skills, and harness" that tells the agent which tier to use for which change — memory for future judgment, skills for on-demand procedure, mods/hooks/permissions/model/crons for runtime enforcement — a taxonomy the harness-RSI papers mostly leave implicit. Read as a spec, it is a claim that the agent's editable surface should be tiered by authority, not that everything should be editable.
  • Recovery over compatibility is the transferable design idea: because the author of a mod is the agent, "compatibility is a migration cost, not a guiding design constraint", and the guarantees offered instead are safe mode, generation-invalidated reload, and diagnostics specific enough for the agent to repair its own broken mod. That is a concrete alternative to the versioned-SDK route taken by general-purpose plugin systems (OpenClaw's capability-registration points, Agent Zero's plugin scanners).
  • Memory-as-a-git-repo is the other one: identity and learning are diffable, revertible, syncable artifacts (`git log` over `$MEMORY_DIR`, `/memory-repository set <git url>` to push context to your own repo) while the immutable recall tier stays harness-owned — an explicit split between what the agent may rewrite and what it may only read. Supporting loop machinery is named and inspectable: `/sleeptime` for periodic dreaming (the sleep-time-compute line), `/doctor [symptom]` plus the context-doctor skill for auditing a grown prompt, and `letta memory tokens --memory-dir <path>` for measuring core-memory size against the ~10%-of-context soft guideline.

Install & run

# requires Node.js 22.19+ (older Node silently installs an older Letta Code)
npm install -g @letta-ai/letta-code
cd your-project && letta                                  # first launch: sign in with Letta or proceed local
letta --new-agent --personality tutorial                  # the built-in tutorial agent
letta setup      # re-choose backend;  letta backend cloud | letta backend local  (--backend cloud|local for a one-off)
letta -p --agent <agent-id> "headless message"             # headless; add --computer "work-laptop" to route to a connected machine
# desktop app (macOS/Windows/Linux) is a separate download, not npm: docs.letta.com/letta-code/desktop-app

Learning note

Open the mods runtime, not the CLI: `src/mods/README.md` (the thesis and the recovery requirements), `src/mods/types.ts` (the mutating event results), and the `creating-mods` skill's `references/`. Then read the "Self-evolution: memory, skills, and harness" section of `src/agent/prompts/letta.md` — that tier taxonomy is the reusable artifact.

Repo README

Letta Code

Letta Code is a stateful agent harness for creating agents that are more like people than tools. Letta Code agents have memory, identity, and a sense of experience over time. They learn and evolve over long horizons through rewriting their own memory, skills, prompts, and even the harness itself (through mods).

Letta Code can be used interactively, or to power always-on agents that work proactively. Interact with agents through:

  • A local CLI
  • The desktop app for macOS, Windows, and Linux
  • Your browser, including mobile, at chat.letta.com
  • Messaging integrations, including Telegram, Slack, Discord, and custom channels

Feature Overview

[!TIP] Letta Code agents are designed to be self-configuring. If you want to configure something (e.g. skills, behavior, hooks, permissions), try asking your agent to do it for you.

Feature Description
Self-improvement & Learning Agents programmatically rewrite their context to improve and adapt over time, including system prompt learning (through memory blocks) and skill learning. Configure periodic dreaming with /sleeptime, investigate agent behavior with /doctor [symptom], and view memory with /palace
Message search Search across all messages and agents with /search. Agent can also search their own conversations or the conversations of other agents
MemFS All context (including memory blocks) is tracked via git. Sync context to a custom GitHub repository by setting /memory-repository set git@github.com:...
Skills Loads global skills (~/.letta), project-scoped skills (.agents/skills), and agent-scoped skills (stored in MemFS). View skills with /skills and create with /skill-creator
Subagents & Multi-agent Call built-in subagents (general-purpose, forked, recall, history-analyzer) in the background. Agents can call any other agent (including themselves) as subagents
Messaging Integrations Chat with the same agent from Slack, Telegram, your browser (chat.letta.com) including mobile, and through custom channels
Hooks Run custom scripts at key points of agent execution to automate workflows
Permissions Set permission modes and customize what actions are auto-approved or auto-denied
Crons & Schedules Configure heartbeats and crons, and let agents work across time with self-managed schedules
Remote computers (requires signing in with Letta) Agents work across multiple computers. Connect any machine by running letta server --computer-name "..."
Secrets (requires signing in with Letta) Make secrets available as environment variables (across machines) while obfuscating their values from context

See the full list of slash commands in our documentation.

Get started

Install the package via npm:

npm install -g @letta-ai/letta-code

Navigate to your project directory and run letta (see command-line options in the docs). You can also run the tutorial agent with: 

letta --new-agent --personality tutorial

Run /connect to configure your own LLM API keys (OpenAI / ChatGPT, Anthropic, Z.ai coding plan, etc.), and use /model to swap models.

You can also download the desktop app for macOS, Windows, and Linux. Agents created in the CLI are available via the desktop app, and vice versa.

Letta Cloud

Agents stored in Letta Cloud keep their memory, identity, and conversations there while the Letta Code harness can run on any connected computer: your laptop, GitHub Actions, a managed cloud sandbox, a remote VM, or a Mac Mini. You can chat with the same agents through chat.letta.com or the desktop app.

graph TD
    LettaCloud["Letta Cloud<br/>Agent state"]
    LettaCloud --> A["💻 Your Laptop"]
    LettaCloud --> B["☁️ Cloud VM"]
    LettaCloud --> C["🖥️ Mac Mini"]
    LettaCloud --> D["📦 Managed Sandbox"]

Run /login from the CLI or sign in through the desktop app to access agents in your Letta account.

Remote computers

Agents stored in Letta Cloud can run across multiple machines. Connect any machine by running:

letta server
letta server --computer-name "work-laptop"

List discoverable computers from the CLI:

letta computers list --online-only

Get the current computer connection for routing another agent onto this same machine:

letta computers current

Route a headless message through a specific computer:

letta -p --agent <agent-id> --computer "work-laptop" "hello from that machine"

Use --computer cloud to start or reuse the target agent's cloud sandbox. Agent-to-agent headless messages without --computer run on the same computer. See our guides for using Railway, DigitalOcean, and Fly.io as remote computers.

The previous environments/envs, --environment/--env, and --env-name spellings remain available for backwards compatibility.

AgentFile deprecation

AgentFile (.af) export and import are deprecated and have been removed from Letta Code. The /export and /download slash commands and the --import and --from-af CLI flags are no longer supported, including imports from the agent registry.

This does not affect memory import/export or conversation transcript export.

Installing external skills

Install skills into a specific agent's memory with letta skills install <skill>:

Source Example
GitHub letta skills install https://github.com/owner/repo
letta skills install https://github.com/owner/repo/tree/main/path/to/skill
letta skills install https://github.com/owner/repo/blob/main/path/to/skill/SKILL.md
ClawHub openclaw skills install <skill-slug> → letta skills install <skill-slug>
Hermes Skills Hub hermes skills install <skill-path> → letta skills install <skill-path>

To view skills run letta skills list --agent <agent-id>, and delete skills with letta skills delete <skill-name> --agent <agent-id>.
