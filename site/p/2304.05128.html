Teaching Large Language Models to Self-Debug

Xinyun Chen, Maxwell Lin, Nathanael Schärli, Denny Zhou

ICLR 2024 · 2024

Local PDFOnline

TL;DR

Self-Debugging teaches an LLM via few-shot prompts to debug its own code by explaining it line-by-line (rubber duck debugging) — no training, no human feedback — lifting Spider 81.3→84.1 and TransCoder baseline by up to 12%.

Abstract

Large language models (LLMs) have achieved impressive performance on code generation. However, for complex programming tasks, generating the correct solution in one go becomes challenging, thus some prior works have designed program repair approaches to improve code generation performance. In this work, we propose Self-Debugging, which teaches a large language model to debug its predicted program via few-shot demonstrations. In particular, we demonstrate that Self-Debugging can teach the large language model to perform rubber duck debugging; i.e., without any human feedback on the code correctness or error messages, the model is able to identify its mistakes by investigating the execution results and explaining the generated code in natural language. Self-Debugging achieves the state-of-the-art performance on several code generation benchmarks, including the Spider dataset for text-to-SQL generation, TransCoder for C++-to-Python translation, and MBPP for text-to-Python generation. On the Spider benchmark where there are no unit tests to verify the correctness of predictions, Self-Debugging with code explanation consistently improves the baseline by 2-3%, and improves the prediction accuracy on problems of the hardest level by 9%. On TransCoder and MBPP where unit tests are available, Self-Debugging improves the baseline accuracy by up to 12%. Meanwhile, by leveraging feedback messages and reusing failed predictions, Self-Debugging notably improves sample efficiency, and can match or outperform baseline models that generate more than 10x candidate programs.

Method

No finetuning: few-shot prompts only, on Codex (code-davinci-002), gpt-3.5-turbo, gpt-4, StarCoder-15.5B. One debugging turn has three steps — Generation (predict program; greedy at τ=0, or τ=0.7 for multiple samples, then execution-based majority vote over non-erroring programs, discarding programs that fail provided unit tests), Explanation (model explains the code in natural language, or writes a line-by-line execution trace of a sample input), Feedback (a correctness message from the model itself, or from unit-test execution). Four feedback formats: Simple (bare "correct"/"wrong" sentence, skipping Explanation), Unit Test (UT; execution results of failed tests in the message), Code Explanation (Expl; rubber-duck line-by-line explanation), Execution Trace (Trace; model-simulated intermediate steps, needing no real execution states). Loop ends when feedback says the code is correct or max 10 turns (successful runs end within 3). For Spider, step 3 compares the inferred question return type against the SQL explanation to emit correctness feedback.

Key results

  • Spider dev (no unit tests), Codex: baseline 81.3 → +Expl. 84.1, beating prompting-only rerankers Coder-Reviewer 74.5 and MBR-Exec 75.2, and the trained T5-3B + N-best Reranking 80.6 and LEVER 81.9 (Table 1a); Simple feedback alone gives 81.3, i.e. zero gain (Table 2a).
  • TransCoder C++→Python pass@1, Codex: 80.4 baseline → 89.3 (Simple) → 91.6 (UT) → 92.5 (UT+Expl.), vs 44.5 TransCoder, 51.8 PaLM, 55.1 PaLM-Coder without debugging (Tables 2b, 6). Trace feedback is worse than UT+Expl. here (87.9).
  • MBPP, Codex: 61.4 → 68.2 (Simple) → 69.4 (UT) → 69.8 (UT+Expl.) → 70.8 (+Trace), vs MBR-Exec 63.0 at n=25, Reviewer 66.9 at n=25, LEVER 68.9 at n=100 — Self-Debugging reaches 72.2 with n=10 samples (Tables 1b, 2c).
  • Sample efficiency (Spider, Codex): Self-Debugging on greedy decoding matches the baseline using 16 samples, and from 8 samples outperforms the 32-sample baseline; one debugging turn captures nearly all the gain (improvement after turn 1 within 0.1%) (Fig. 6a, §5.2.1).
  • Ablations: +9% on Spider extra-hard problems (Fig. 6b), the largest fixed-error classes being wrong WHERE conditions 25.7% and missing DISTINCT 17.1% (Table 4); without unit-test execution (Table 3) Codex still gains on TransCoder (80.4 → 83.9 with Expl.) but regresses on MBPP under Simple feedback (61.4 → 57.6, recovering to 66.2 with Trace), while GPT-4 MBPP improves 72.8 → 76.4.

Key advantages

  • Establishes that self-debugging needs no training and no human feedback: a few-shot prompt makes the model emit its own explanations and correctness verdicts, and this alone beats trained rerankers on Spider (84.1 vs LEVER 81.9) and trained code-repair models.
  • Isolates *why* it works: on Spider, where no oracle exists, bare Simple feedback yields literally no improvement (81.3 → 81.3) because the model cannot tell correct from incorrect SQL; adding line-by-line code explanation is what supplies the signal. Explanation, not the iterate-again loop, does the work.
  • Improves sample efficiency rather than just peak accuracy: debugging from 8 samples beats sampling 32 without debugging, so the same accuracy is bought with ~4× fewer samples — a direct compute-efficiency argument for iterative repair over naive reranking.
  • Execution Trace feedback is generated by the model, not the interpreter, so it needs no access to intermediate execution states — a cheap stand-in for real traces that still helps. And the method transfers to an open 15.5B model: StarCoder gains ~6% on MBPP with trace feedback (47.2 → 53.2).

Limitations

  • Execution is load-bearing, and removing it can make things worse: on MBPP with Codex, no-execution Simple feedback *drops* accuracy from 61.4 to 57.6, and the paper reports GPT-3.5/GPT-4 are "overconfident in their own initial predictions" without unit-test execution, with few-shot prompting not notably helping their self-debugging.
  • Richer feedback is not monotonically better and is budget-constrained: Trace underperforms UT+Expl. on TransCoder (87.9 vs 92.5 vs 91.6 for plain UT), and adding explanations shrinks the prompt to 3 exemplars vs 6 for simple/UT feedback, which the paper gives as a reason explanation helps less on MBPP.
  • Explanation helps least exactly where it would matter most — the paper notes it "plays a smaller role when the initial predicted code is far from the correct solution," where the model just rewrites from scratch. Scope is single-function/query tasks (Spider dev, MBPP, TransCoder) and per-turn generation cost is never quantified.
  • The paper has no limitations or broader-impact section (§7 gives only future work, and notes preliminary results that model-generated *semantic-error* feedback adds nothing over line-by-line explanation). It is also prompt-format sensitive: GPT-4, far stronger than Codex generally, scores only 73.2 on Spider few-shot vs Codex 81.3, both before and after debugging.
