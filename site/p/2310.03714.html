DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines

Omar Khattab, Arnav Singhvi, Paridhi Maheshwari, Zhiyuan Zhang, Keshav Santhanam, Sri Vardhamanan, Saiful Haq, Ashutosh Sharma, Thomas T. Joshi, Hanna Moazam, Heather Miller, Matei Zaharia, Christopher Potts

NeurIPS 2023 (R0-FoMo) · 2023

Local PDFOnline

TL;DR

DSPy replaces hand-written prompt strings with typed signatures, parameterized modules, and teleprompters that compile a pipeline against a metric, bootstrapping demonstrations so GPT-3.5 and llama2-13b-chat self-improve GSM8K and HotPotQA programs without prompt engineering.

Abstract

The ML community is rapidly exploring techniques for prompting language models (LMs) and for stacking them into pipelines that solve complex tasks. Unfortunately, existing LM pipelines are typically implemented using hard-coded "prompt templates", i.e. lengthy strings discovered via trial and error. Toward a more systematic approach for developing and optimizing LM pipelines, we introduce DSPy, a programming model that abstracts LM pipelines as text transformation graphs, i.e. imperative computational graphs where LMs are invoked through declarative modules. DSPy modules are parameterized, meaning they can learn (by creating and collecting demonstrations) how to apply compositions of prompting, finetuning, augmentation, and reasoning techniques. We design a compiler that will optimize any DSPy pipeline to maximize a given metric. We conduct two case studies, showing that succinct DSPy programs can express and optimize sophisticated LM pipelines that reason about math word problems, tackle multi-hop retrieval, answer complex questions, and control agent loops. Within minutes of compiling, a few lines of DSPy allow GPT-3.5 and llama2-13b-chat to self-bootstrap pipelines that outperform standard few-shot prompting (generally by over 25% and 65%, respectively) and pipelines with expert-created demonstrations (by up to 5-46% and 16-40%, respectively). On top of that, DSPy programs compiled to open and relatively small LMs like 770M-parameter T5 and llama2-13b-chat are competitive with approaches that rely on expert-written prompt chains for proprietary GPT-3.5. DSPy is available at https://github.com/stanfordnlp/dspy

Method

A program declares Signatures: typed input/output fields like "question -> answer", not prompt strings. Modules wrap a signature — Predict formats signature plus demonstrations into a prompt, calls the LM, parses output fields, and in compile mode records input/output traces. ChainOfThought merely prepends a rationale output field and delegates to Predict; ReAct, ProgramOfThought and MultiChainComparison are likewise built from Predict. Modules compose in a define-by-run forward() method (retrieve, then answer). A teleprompter compiles the program given a trainset plus metric in three stages: (1) candidate generation — recursively find unique Predict modules, simulate the program, and keep multi-stage traces whose final output passes the metric as demonstrations for each signature; (2) parameter optimization — select demonstration sets by random search or Optuna, or update LM weights via BootstrapFinetune; (3) higher-order optimization — ensemble the top bootstrapped programs by majority voting. What evolves is demonstrations and field instructions, not weights, unless finetuning.

Key results

  • GSM8K, GPT-3.5 dev/test: vanilla zero-shot 24.0 → bootstrap×2 64.7/61.7; CoT 50.0 → bootstrap 80.3/72.9 → +ensemble 88.3/81.6, matching the 8-shot fewshot+human-CoT baseline (78.6/72.4); reflection (5 sampled chains compared by MultiChainComparison) 83.0/76.0 and 86.7 dev ensembled. The paper's summary: composing modules instead of strings lifts LMs from 4-20% to 49-88% accuracy.
  • GSM8K, llama2-13b-chat dev/test: vanilla 7.0/9.4 → bootstrap×2 37.3/36.5; CoT 26.7 → bootstrap 43.3 (+ensemble 43.7 dev) vs 34.3 with human CoT demonstrations; reflection 36.7 → 44.3 bootstrap / 49.0 ensembled, 40.2/46.9 test.
  • HotPotQA answer EM, GPT-3.5 dev/test: CoT RAG fewshot 36.4 → bootstrap 42.3; multihop (two-hop query generation) 36.9 → 48.7 bootstrap (47.0 passage accuracy) → 54.7 ensemble dev, 31.2 → 39.6 → 45.6 test (ensemble scored on 50% of test due to cost). llama2-13b-chat multihop: 34.7 → 42.0 → 50.0 dev, 31.3 → 36.4 → 41.0 test.
  • HotPotQA ReAct dev EM: GPT-3.5 zero-shot 20.3, +human reasoning 33.0, bootstrap 31.0, bootstrap×2 39.0; llama2-13b-chat 20.0, 28.3, 24.7, 40.0 — bootstrap×2 beats the expert-written ReAct traces.
  • BootstrapFinetune distils a multihop program into T5-Large (770M): 39.3% answer EM and 46.0% passage accuracy on dev, from 200 labeled inputs plus 800 unlabeled questions and a teacher that is an ensemble of two llama2-13b-chat multihop programs.

Key advantages

  • Prompt strings stop being the interface: the same two-to-four-module programs and the same compilers run on GPT-3.5 and llama2-13b-chat, and bootstrapped demonstrations match or beat expert-written ones (GSM8K CoT 80.3 vs 78.6 dev with human CoT; llama2-13b-chat CoT 43.3 vs 34.3).
  • Label-efficiency by construction: only final-output labels are assumed, while intermediate reasoning chains and retrieval contexts are bootstrapped, so a new pipeline is recompiled rather than re-annotated with step-specific data.
  • Compiling closes the LM gap — llama2-13b-chat multihop at 42.0 dev EM vs GPT-3.5 fewshot at 36.9 — and BootstrapFinetune pushes the pipeline into a 770M T5, which the paper argues means orders-of-magnitude cheaper inference than a proprietary LM.
  • One optimizer abstraction covers prompting and finetuning, and a teacher program can be composed in (an expensive large-LM ensemble supervises a cheap student), which is what makes the T5 result possible.

Limitations

  • A well-defined automatic metric plus at least a few training inputs the LM can actually pass are prerequisites; bootstrapping works by rejection-sampling traces that satisfy the metric, so a program (or LM) that never passes yields no demonstrations.
  • The empirical evidence is two case studies, GSM8K and HotPotQA; the conclusion explicitly defers other tasks (information extraction, low-resource synthetic data generation) to future work.
  • Compiling is not free: minutes to tens of minutes and thousands of program runs (10-20 trials over 150-300 validation examples), and it was costly enough that the HotPotQA ensemble test number is marked as evaluated on 50% of the test set.
  • The optimizer scope in this version is narrow: "In this iteration of DSPy, we focus on demonstrations", Stage 3 control-flow optimization is only ensembling (dynamic test-time bootstrapping and backtracking are future work), and optional field data types are "not core to DSPy at the time of writing".
