PAPER · stage 7 · Coding / Software-Engineering Self-Improvement

A Self-Improving Coding Agent

Maxime Robeyns, Martin Szummer, Laurence Aitchison

ICLR 2025 (SSI-FM Workshop) · 2025

Local PDFOnline

TL;DR

SICA: a coding agent edits its own full Python codebase — no DSL, no weight updates. The best-scoring agent in the archive becomes the meta-agent that writes the next version, lifting a SWE-bench Verified subset from 17% to 53%.

Abstract

Recent advancements in Large Language Models (LLMs) have spurred interest in deploying LLM agents to undertake tasks in the world. LLMs are often deployed in agent systems: code that orchestrates LLM calls and provides them with tools. We demonstrate that an agent system, equipped with basic coding tools, can autonomously edit itself, and thereby improve its performance on benchmark tasks. We find performance gains from 17% to 53% on a random subset of SWE Bench Verified, with additional performance gains on LiveCodeBench, as well as synthetically generated agent benchmarks. Our work represents an advancement in the automated and open-ended design of agentic systems, and demonstrates a data-efficient, non gradient-based learning mechanism driven by LLM reflection and code updates.

Method

SICA starts as an ordinary Python coding agent: a main orchestrator plus software-developer, problem-solver and reasoning sub-agents; tools to open/close/overwrite files, run shell commands, calculate and submit answers; and a context laid out (system prompt, core prompt, appended assistant messages) to preserve the KV cache across tool calls. A benchmark runner evaluates each agent version on four tasks — synthetic file editing, synthetic symbol navigation, SWE-bench Verified, LiveCodeBench — and files scores in an archive. Then Algorithm 1: pick the archive member maximising U = 0.5·score + 0.25·(1 − min(1, cost/$10)) + 0.25·(1 − min(1, time/300 s)), with a τ = 0.5 penalty on timeouts, and run it as the meta-agent to write the next version. Nothing is trained: edits are code and prompt changes anywhere in the repository. An asynchronous LLM overseer samples the trace every 30 s and may notify or cancel a stuck agent.

Key results

  • SWE-bench Verified, fixed random 50-question subset: 0.17 accuracy at iteration 0 → 0.53 at iteration 14 (0.51 at iteration 15) — the headline 17% → 53%, vs 0.14–0.47 over the intermediate iterations.
  • Synthetic in-codebase benchmarks: file editing 0.82 → 0.96 (iteration 6); symbol navigation 0.35 → 0.43 (iteration 11), with the paper attributing the low absolute scores partly to bad data (some target symbols live in uninstalled external libraries).
  • LiveCodeBench, 50 random questions: 0.65 → 0.70/0.71 — a subtle gain, the benchmark least responsive to scaffolding, since its competitive-programming tasks lean on model reasoning rather than agent structure.
  • Cost and speed move the right way, because 25% of utility each is spent on them: mean per-problem $1.91 and 130.2 s at iteration 0 → $1.70 and 114.5 s at iteration 15 (best $1.58 and 103.9 s at iteration 12).
  • Reasoning tasks saturate instead: o3-mini alone scores 87% on AIME 2024 and 79% on GPQA Diamond at high reasoning effort, while the agent system averaged 76% across the two, with 9 iterations finding little (Figure 4). The 15-iteration run cost roughly $7,000 in API spend.

Key advantages

  • Genuinely self-referential, not two-agent search: ADAS fixes a meta-agent that edits a single forward function in a purpose-built DSL, whereas SICA takes its meta-agent from the archive (arg max utility) and lets it edit its whole Python codebase — prompts, tools, sub-agents and orchestration — with no DSL (this also separates it from Gödel Agent's special-purpose logic tools and STOP's algorithmic-task setting).
  • Non-gradient, data-efficient learning: gradients are never touched, so each expensive iteration must earn its gain by reading the full archive and committing one substantial, verifiable code change — and the paper presents the absence of weight updates, plus the overseer and observability UI, as its central safety mitigation.
  • Discoverable artifacts, not vague wins: Appendix D names the 14 edits — SmartEditor, quick-overwrite, diff-enhanced editing, CodeContextSummarizer over ripgrep, InputNormalizer, enhanced file-edit verification, minimal-diff output, an AST Symbol Locator at iteration 9, then a hybrid ripgrep-candidate + AST-verified locator and a 100 KB file-size threshold — so the trajectory shows the agent building its own codebase-navigation and token-efficiency tooling.
  • Cost and wall-clock are first-class in the objective rather than afterthoughts, which is why accuracy gains arrive alongside flat-to-lower per-problem time and dollars instead of being bought with budget.

Limitations

  • Idea generation is the bottleneck (§5.1, the paper's own account): the agent struggles to propose genuinely novel, feasible modifications, and initial feature ideas path-depend later ones as variations on the same theme (e.g. fixating on caching open files), making runs high-variance — while a bad idea costs both a long editing session and a full benchmark sweep.
  • The caps distort the baseline: 300 s timeouts (called "5-minute timeouts") and $10-per-problem limits mean iteration-0 scores undersell Sonnet 3.5 v2, especially on SWE-bench, and much of the reported improvement comes from speed and token-efficiency features that SWE-bench accuracy does not reflect.
  • No reasoning gains and possible harm: on AIME 2024/GPQA Diamond the agent mostly delegates to the o3-mini reasoning sub-agent and saturates, and the authors speculate the crude reasoning-inducing components can interrupt a reasoning model's chain of thought and lower scores.
  • Evidence is thin and static: one 15-iteration run on 50-question subsets, no seeds or variance reported, no weight updates at all, and the authors expect saturation on a fixed benchmark set, leaving agent-authored benchmarks (the two synthetic tasks) as a proof of flexibility rather than a scaled solution.
