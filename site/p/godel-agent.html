Gödel Agent

repo

GitHub

What it does

Gödel Agent — a self-referential agent whose behavior is code it can inspect and rewrite: its actions, prompts and solver are Python it reads, patches at runtime, and re-evaluates in a loop (arXiv 2410.04444).

How it works

  • src/agent_module.py is the whole agent (~724 lines): Agent(AgentBase) plus its own tool schema list agent.action_functions — action_read_logic (inspect.getsource on itself), action_adjust_logic (exec + setattr on the live module/class, keeping a __source__ map so rewritten methods stay readable), action_run_code, action_evaluate_on_task.
  • Loop in src/main.py: reinit() feeds the agent its own solver source, then evolve() prompts o3 with tools=agent.action_functions, tool_choice='required' — the model must act; action_counter['evolve'] >= 100 hard-exits the run.
  • Validation is accuracy-gated checkpointing: action_evaluate_on_task calls task.evaluate(solver); only when accuracy beats task_mgsm.last_test_acc does logic.store_all_logic() dump the current in-memory agent to results/<task>/agent_module/ (drop_80.892.txt, gpqa_0.3494.txt, mmlu_0.7087.txt, mgsm_0.6425.txt).
  • Eval harnesses src/task_{mgsm,mmlu,gpqa,drop}.py are adapted from ADAS; src/goal_prompt.md tells the model literally that it is the self_evolving_agent instance of Agent in module agent_module — self-reference by address, not metaphor.

Key advantages

  • Purest code-as-identity artifact in this catalog: no outer harness owns the improvement loop — the agent edits the very module it executes from, so monkey-patching, runtime guardrails and self-inspection are all directly observable in one readable file.
  • results/ ships the evolved agent per benchmark, so you can diff what a run actually changed (e.g. the DROP solver it grew from a one-shot gpt-4o-mini prompt into a 5-sample self-consistency ensemble) before spending API money.
  • Edit-time safety is explicit and small: what the framework forbids (rewriting action_call_llm / action_call_json_format_llm, time.sleep in solver, logging) is exactly the guardrail-boundary question RRSI cares about.

Learning note

Read results/*/agent_module/ first — the evolved DROP/MMLU solvers show what the loop actually finds. Then study action_adjust_logic's guardrails and the accuracy-gated store_all_logic checkpoint. Theory-side companion to DGM; here self-reference is literal: the agent is the module it edits.

Method Overview

Installation

  1. Clone the repository:

    git clone https://github.com/Arvid-pku/Godel_Agent.git
cd Godel_Agent

  2. Install dependencies via pip:

    pip install -r requirements.txt

  3. Navigate to the source directory and run the main script:

    python src/main.py
# You can adjust the task in the agent_module.py file.

Project Structure

  • datasets/: This folder contains the datasets used in the experiments.

  • results/: Stores the self-optimized code generated by the model during each task, as well as the output generated by the model during tests.

  • src/: This folder contains the code implementation.

    • main.py: The entry point for running the agent.
    • agent_module.py: Core implementation of the Gödel Agent, including the self-awareness, self-modification, and action execution logic.
    • task_*.py: Evaluation scripts for each task/environment. (adapted from ADAS)
    • logic.py: Stores the generated agent code.
    • wrap.py: Used for debugging.
    • goal_prompt.md: Contains the goal prompt for the agent.

Configuration

Make sure to configure your OpenAI API key in the key.env file before running the code.

Development Tips

  1. When you want to add a new action, you need to:
    a. Add an entry to the agent.action_functions list, including the name, parameters, return value, and functional description of the action you are adding, to facilitate LLM invocation.
    b. Implement the action function.
    c. (Optional) Emphasize it in the goal_prompt to encourage the agent to call this action under certain conditions.

  2. When you want to use the Godel Agent in a new environment, you need to:
    a. Define some reward functions, where the input is the agent's policy and the output is feedback to the agent, such as scores, suggestions, or scenario descriptions.
    b. Implement the action_evaluate_on_task function for that environment.
    c. Implement the initial policy, which can be simple. The current implementation is the solver function (you can reflect the environment in which the policy is applied within the solver or describe the environment in the goal_prompt).

  3. If you want the Godel Agent to perform multiple tasks in a complex environment, you need to implement different initial solvers and different action_evaluate_on_task functions. Note that action_evaluate_on_task is also an action and needs to be added as described in the first point.
